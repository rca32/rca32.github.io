よい売買アイデアは、いつよいアイデアになるのだろうか。

チャート上でそれらしく見えた時ではない。何度か当たった時でも、まだ早い。よい売買アイデアは、ルールになり、コードになり、過去データとリアルタイム条件の両方で同じ方法で検証できるようになった時、ようやくよいアイデアに近づく。

だから TradingView ユーザーにとって、Pine Script は単なるスクリプト言語ではない。考えを検証可能な形に変える、小さな実験室である。

多くのトレーダーは、すでに半分は戦略家のように働いている。移動平均線がある角度で広がる時、RSI が特定のゾーンから反転する時、出来高が直近のレンジより大きくなる時、人は頭の中で条件式を作っている。問題は、その条件式が言葉のまま残ることだ。記憶はうまく見えた場面をよく保存し、悪かった場面を早く消してしまう。

コードはその逆をする。コードは気に入らなかった区間も数える。曖昧なエントリーも数える。損切りの直後に反発した場面も数えてしまう。だから不快だ。しかし売買では、この不快さに価値がある。

ここで大事な区別がある。チャート分析には二つの仕事が混ざっている。一つはパターンを見ること。もう一つは、そのパターンが反復可能かを確かめることだ。人間は一つ目の仕事に強い。エージェントは二つ目の仕事を担う時に強くなる。

売買におけるエージェントの仕事は「上がる銘柄を当てること」ではない。それは定義として弱すぎる。より重要なのは、ユーザーの仮説を Pine Script の戦略に変え、バックテスト、アラート条件、リスク条件を一つの流れにまとめることだ。

たとえば、こんなアイデアがあるとする。

> 終値が20日移動平均線の上にあり、出来高が直近平均より大きい時だけ、ブレイクアウトを買う。

これは戦略のように見える。だが実際には、多くのものが抜けている。移動平均線の上とは終値基準か、ザラ場基準か。出来高平均は何本で計算するのか。ブレイクアウトは直近高値なのか、レンジ上限なのか。損切りはどこに置くのか。利確は固定比率なのか、トレンド離脱なのか。同じ足でエントリーと決済が起きてもよいのか。

こうした質問が面倒に感じられるのは自然だ。しかし、その面倒な部分に戦略の大部分が隠れている。アイデアはたいてい一文から始まる。戦略は何十もの小さな決定からできている。

Pine Script が重要なのは、この小さな決定を表に出すからだ。`strategy.entry()` をどこで呼ぶのかを決めなければならない。損切りと利確をどう置くかも決めなければならない。アラートをいつ鳴らすかも決めなければならない。言葉では一つの「ブレイクアウト戦略」でも、コードでは複数の別々の戦略に分かれる。

ここでエージェントの居場所が見えてくる。エージェントは、ユーザーの最初の一文を完成した戦略として扱ってはいけない。むしろ、その一文の中にある空白を見つけるべきだ。よいエージェントは、コードを速く書く道具というより、抜けている条件を最後まで問い続ける道具に近い。

TradingView では、特に三つの点に注意する必要がある。

一つ目はリペイントだ。これは「リペイントするか、しないか」と聞くだけでは足りない。TradingView の公式文書でも、リペイントには多くの原因と形があると説明されている。よりよい質問は具体的でなければならない。過去足とリアルタイム足で同じように計算されるか。アラートは足の確定を待つか。`request.security()` が過去データに未来の情報を漏らしていないか。

二つ目は約定の仮定だ。バックテストは実際の板ではない。TradingView の戦略は broker emulator によって理論上の約定を計算する。Bar Magnifier のような機能は、より低い時間足のデータを使って約定の仮定を細かくできるが、それでも実際のスリッページや流動性を完全に置き換えるものではない。

三つ目は実行経路だ。Pine Script の戦略やインジケーターは、取引所に直接注文を出すシステムではない。TradingView の公式文書によれば、戦略とインジケーターは TradingView のブローカー連携や内蔵のペーパートレード口座に直接注文を出すことはできない。実運用の自動化は通常、アラート、Webhook、外部の実行システムを使う別レイヤーとして設計する必要がある。

この三つは初心者を脅すための警告ではない。むしろ、専門的な売買システムを作るための最低限の床である。戦略の収益率という数字は、この床の上にある時だけ意味を持つ。

AI エージェントの流れも、ここにつながっている。最近の金融業界における AI の議論は、単純なチャットボットから離れつつある。レポートを要約する道具よりも、複数のシステムをまたいで作業を計画し実行するエージェントが大きなテーマになっている。金融では特に、リスク管理、コンプライアンス、投資戦略の最適化のように、ルールと例外が同時に存在する仕事がエージェントに向いている。

個人トレーダーにも、同じ変化が起きる可能性が高い。以前は、よいインジケーターを見つけることが優位性だった。これからは、よい仮説をどれだけ早くコードにし、どれだけ正直に検証し、どれだけ早く修正できるかがより重要になる。

私はこの流れを「チャート読みから戦略コンパイルへの移動」と見ている。コンパイルという言葉は少し硬く聞こえるかもしれないが、意味は単純だ。頭の中にあった売買の考えを、実行可能なルールに変えることである。文章をコードにコンパイルするように、売買アイデアも Pine Script にコンパイルされるべきだ。

その過程で、エージェントは四つの仕事を繰り返すことになる。

  <img src="/assets/images/posts/trading-idea-to-pine-script/execution-risk.png" alt="チャートシグナルがアラートと外部実行レイヤーへ流れる構造を示すリサーチ画像" loading="lazy" decoding="async">
  <figcaption>Pine Script のシグナルと実際の注文実行は別のレイヤーである。真面目な自動化は、その経路を明示的に設計する。</figcaption>
</figure>

1. ユーザーの売買アイデアを明示的な条件に分解する。
2. その条件を Pine Script のインジケーターまたは戦略として書く。
3. リペイント、約定の仮定、アラート条件、ポジション管理の抜けを点検する。
4. バックテスト結果をもとに次の実験を提案する。

このループが重要なのは、収益率をすぐ保証するからではない。むしろ逆だ。多くの戦略はこのループを通ることで、弱いことが明らかになる。それはよいことだ。弱い戦略を早く捨てる能力は、強い戦略を見つける能力の一部である。

このブログでは、これからこのループを扱っていく。Pine Script の文法だけを説明するつもりはない。チャートパターンだけを並べるつもりもない。エージェントが売買アイデアをどう構造化し、戦略コードをどう作り、バックテストの数字をどう疑うべきかを扱う。

トレードで最も危険な文は「感覚的にうまくいく」だ。二番目に危険な文は「バックテストの収益率が高い」だ。どちらも、まだ十分ではない。

よい売買アイデアはコードになるべきだ。そして、よいコードはもう一度疑われるべきだ。その反復をより速く、より厳密にすることが、チャート上でエージェントができる最も現実的な仕事である。
